# Multiple boards: team boards, custom stages and handover to dev

## Context

Some teams don't ship code. SEO and DevOps run their work in Trello today, and we want them
in Glideship. Product and design people also want their own boards with a few stages, ending in
a handover that puts the work on the dev board.

Today Glideship has exactly one board: the BUD board (`views/buds/BUDBoard.vue`). Its columns
come from the fixed `BUDStatus` enum. That enum has ten values, not the eight the root
CLAUDE.md lists:
`bud → design → tech_arch → development → code_review → testing → uat → prod → closed`, plus
`discarded` (`models/bud.py:79-91`).

That lifecycle is load-bearing. 52 modules import `BUDStatus` and about nine more use raw
status strings. They cover:

- PATCH guards and QA scope (`api/v1/bud.py`)
- agent triggers (`agents/skill_mapping.py`, `agent_skill_bud_stages`)
- PR auto-transitions (`services/pr_auto_transition.py`)
- release detection and auto-close (`services/release_detection.py`)
- XP and SP on close (`services/bud_closure.py`, `sp_pm.py`, `sp_tech_arch.py`)
- learning metrics (`services/bud_metrics_phases.py`)
- estimation and velocity, which rely on the enum's iteration order (`repositories/bud_estimate.py:106`)
- standups, assignment and phase-edit locks

Whatever we build must leave all of that untouched.

This document is a plan only. Nothing here has been implemented.

## Decisions so far

These come from the first review of this plan. The sections below already reflect them.

| Question | Decision |
|---|---|
| One card to several BUDs? | Yes. A card can hand over to, or link, any number of BUDs. |
| Where does a handover land? | It can skip ahead. The target is `bud`, `design` or `tech_arch`, with a default set per board and changeable in the dialog. |
| Board membership | Both. Add whole teams and individual people. |
| Landing page | Users without engineering access land on `/boards` when they belong to at least one board. |
| New `notification_type` values | Add the `ALTER TYPE ... ADD VALUE` lines to the autogenerated revision, as `z4_add_code_review_and_commits` does. |
| Trello API import | Build it, alongside the JSON upload. |
| Due-date reminders on Slack | Yes, in the first release. |
| Garden | Board activity shows up there, with no XP. Anyone with `boards:view` can open the Garden, not only engineering users. |
| Drag and drop | Use a library. |
| Card fields | Add priority and start date. |
| Moving cards between boards | Yes, in the first release. |
| AI | Each board stage can run an AI skill, configured per stage. Its output waits as a draft for a person to accept. First skills: writing a PRD and helping with initial design. |
| Autonomous AI | Not in this plan. It's for later (see Later: autonomous work). |
| Who can hand over? | Only people with `buds:create`. |

## Research summary

### How other tools model it

**Per-team stages, with a fixed category behind each one.** Every mature tool lets a team name
its own stages but forces each stage into a small fixed set of categories, and reports on the
categories only:

| Tool | Categories |
|---|---|
| Jira | To Do, In Progress, Done (fixed, can't add more) ([statuses](https://www.herocoders.com/blog/understanding-jira-issue-statuses)) |
| Linear | Triage, Backlog, Unstarted, Started, Completed, Canceled ([configuring workflows](https://linear.app/docs/configuring-workflows)) |
| Shortcut | Backlog, Unstarted, Started, Done; "the type determines how Stories in that state are counted and reported" ([workflows](https://www.shortcut.com/help/fields-and-features/workflows)) |
| ClickUp | Not Started, Active, Done, Closed ([statuses](https://help.clickup.com/hc/en-us/articles/6309452618647-Manage-task-statuses)) |
| Trello | None. A list is just a name. |

**Moving work across boards loses context.**
- Trello: moving a card keeps the description, checklists, attachments and comments. It drops
  card history and any members who aren't on the target board, and board-scoped custom fields
  vanish ([moving cards](https://support.atlassian.com/trello/docs/moving-cards-or-lists/),
  [TRELLO-955](https://jira.atlassian.com/browse/TRELLO-955)).
- Linear: moving an issue gives it a new ID (old URLs redirect). It maps the status to the
  closest match and drops team labels and projects
  ([move to new team](https://linear.app/docs/move-to-new-team)).
- Jira: moving between projects changes keys and needs status mapping. Atlassian warns you
  "may lose data" when workflows differ
  ([bulk move](https://support.atlassian.com/jira-software-cloud/docs/move-multiple-issues/)).

**Linking beats moving for product-to-delivery handover.** Jira Product Discovery doesn't move
ideas. From an idea you "Create work item" in a delivery project, optionally copying the idea's
description, or link an existing one. The idea then shows delivery progress rolled up from the
linked work
([create delivery work](https://support.atlassian.com/jira-product-discovery/docs/create-a-jira-issue-from-jira-product-discovery),
[delivery progress](https://support.atlassian.com/jira-product-discovery/docs/configure-the-delivery-progress-field)).
Two limits:
- The idea's own status doesn't follow delivery without hand-built automation
  ([delivery automation](https://support.atlassian.com/jira-product-discovery/docs/automate-actions-in-the-delivery-panel/)).
- The roll-up silently breaks when a status has no category
  ([community case](https://community.atlassian.com/forums/Jira-Product-Discovery-questions/Jira-Product-Discovery-Delivery-Progress-Ignores-To-Do-Child/qaa-p/3174205)).

**Intake inboxes.** Linear puts incoming work from other teams into the receiving team's Triage,
where someone accepts, declines or merges it as a duplicate
([triage](https://linear.app/docs/triage)).

**Multi-homing has a cost.** Asana and ClickUp let one task sit in several projects or lists,
but the task has a single shared status. Teams end up duplicating tasks to get independent
status, and ClickUp lets the home list decide the statuses
([Asana multi-homing](https://help.asana.com/s/article/how-to-multi-home-tasks),
[ClickUp multiple lists](https://help.clickup.com/hc/en-us/articles/6309958824727-Tasks-in-Multiple-Lists)).
GitHub Projects keeps a per-project single-select Status field
([single select](https://docs.github.com/en/issues/planning-and-tracking-with-projects/understanding-fields/about-single-select-fields)).

**WIP limits are soft.** Jira column limits only turn the column red or yellow
([configure columns](https://support.atlassian.com/jira-software-cloud/docs/configure-columns/)).
Trello's List Limits Power-Up only recolours the list.

**Visibility comes in three levels.**
- Trello: private, workspace or public
  ([visibility](https://support.atlassian.com/trello/docs/changing-the-visibility-of-a-board/)).
- Jira team-managed projects: open, limited (view and comment) or private
  ([access](https://support.atlassian.com/jira-software-cloud/docs/manage-how-people-access-your-team-managed-project/)).

### Trello import facts

**JSON board export.**
- Any member can export a board, but the export holds only the most recent 1,000 actions, and
  comments are actions. Older comments are dropped without warning
  ([export](https://support.atlassian.com/trello/docs/exporting-data-from-trello),
  [PLANKA note](https://docs.planka.cloud/docs/configuration/importing-from-trello)).
- Attachments are links to Trello-hosted files.
- Trello publishes no schema. The keys `actions`, `cards`, `lists`, `labels`, `members`,
  `checklists` and `customFields` match common knowledge but need checking against a real
  export.
- Card fields include `idList`, `idLabels`, `idMembers`, `due`, `dueComplete`, `start`, `closed`
  (archived), `pos`, `desc` (up to 16,384 chars) and `idShort`
  ([object definitions](https://developer.atlassian.com/cloud/trello/guides/rest-api/object-definitions/)).

**REST API.**
- Board data comes nested from
  `GET /1/boards/{id}?cards=all&lists=all&labels=all&members=all&checklists=all&card_attachments=true`
  ([nested resources](https://developer.atlassian.com/cloud/trello/guides/rest-api/nested-resources/)).
- Comments come from `/1/boards/{id}/actions?filter=commentCard&limit=1000`, paged with
  `before`. The `page` parameter is ignored
  ([limits](https://developer.atlassian.com/cloud/trello/guides/rest-api/limits/)).
- Auth is an API key plus a user token (scopes `read`/`write`/`account`, expiry from `1hour` to
  `never`), or OAuth 1.0
  ([authorization](https://developer.atlassian.com/cloud/trello/guides/rest-api/authorization/)).
- Uploaded attachment files need an `Authorization: OAuth ...` header to download
  ([announcement](https://community.developer.atlassian.com/t/update-authenticated-access-to-s3/43681)).

**Rate limits.**
- 300 requests per 10 s per key, and 100 per 10 s per token.
- Going over returns 429. More than 200 429s blocks the key for the rest of the window
  ([rate limits](https://developer.atlassian.com/cloud/trello/guides/rest-api/rate-limits/)).

**Webhooks.**
- They need a public callback URL that answers a HEAD check, and are signed with HMAC-SHA1
  ([webhooks](https://developer.atlassian.com/cloud/trello/guides/rest-api/webhooks/)).
- Local-first installs often have no public URL.

**How other importers behave.**
- Jira collapses lists to To Do / In Progress / Done, and has a bug that put every card in To Do
  ([import](https://support.atlassian.com/jira-cloud-administration/docs/import-data-from-trello/),
  [JRACLOUD-94153](https://jira.atlassian.com/browse/JRACLOUD-94153)).
- Linear appends comments and attachments to the description and seems to ignore lists
  ([importer](https://github.com/linear/linear/blob/master/packages/import/README.md)).
- Shortcut creates duplicates if you import twice
  ([help](https://www.shortcut.com/help/admin/import-from-trello/)).
- Two-way sync is something vendors sell (Unito), and Trello itself warns that rule-based
  two-way sync can loop
  ([sync](https://support.atlassian.com/trello/docs/synchronizing-cards/)).

### Pitfalls teams report

- **Status sprawl.** Near-duplicate workflows pile up, and once there are too many statuses,
  cross-team reports become apples versus oranges. Advice: 6 to 9 core statuses, with edge
  cases in labels
  ([anti-patterns](https://community.atlassian.com/forums/discussion/3138593/10-jira-status-anti-patterns-and-the-10-minute-fix-for-each)).
- **Category drift.** The same logical status mapped to different categories quietly skews
  cycle time
  ([drift](https://community.atlassian.com/forums/App-Central-discussions/Your-Jira-configuration-doesn-t-stay-correct-It-drifts/td-p/3264677)).
  Removing or remapping a status rewrites sprint history
  ([KB](https://support.atlassian.com/jira/kb/sprint-report-inaccuracies-after-workflow-change/)).
- **Duplicates after handover.** Copies drift apart, clones lose comments, and importers
  duplicate on re-run.
- **Lost context and bounce-backs.** Over-the-wall handoffs cause rework. The usual fixes are
  a readiness gate, one discussion thread, and sending work back only for structural problems
  ([handoff](https://miro.com/software-development/developer-designer-handoff/)).
- **Ownership confusion.** When there are mirrors or copies, nobody is sure which one is
  authoritative.

## Options considered

1. **BUDs with custom stages per board.** Add a `board_id` and a user-defined stage to
   `BUDDocument`, and map custom stages onto `BUDStatus`.
   - Rejected. 52+ modules branch on `BUDStatus` values and their order.
   - Every BUD drags along requirements, tech spec, test plan, an embedding, agents, numbering
     and SP rules that mean nothing to an SEO task.
   - A custom-stage BUD would either fake a real status, which corrupts velocity and
     estimation, or need a null status, which every one of those modules would have to learn
     about.
2. **A generic "work item" that replaces the BUD, with the dev lifecycle as one workflow among
   many.** This is the Jira or Linear shape.
   - Rejected for now. It means rewriting the core domain object and every dependent above.
   - It also breaks the rule that the BUD keeps its name.
3. **A new lightweight card on new boards, with the BUD board left as the fixed delivery board,
   and a handover that creates (or links) a BUD.** *Recommended.*

### Recommendation

**Cards on boards.**
- Non-code and pre-dev teams get **boards** that hold **cards**, a new lightweight object with a
  title, markdown description, assignees, labels, priority, start and due dates, checklist,
  comments, attachments, documents (a PRD, a design brief) and activity.
- Each board defines its own **stages** as rows.
- Each stage carries a **category** from a Postgres enum (`todo`, `in_progress`, `done`,
  `canceled`), and all reporting runs on the category.

**The BUD board stays exactly as it is.**
- It shows up in the boards list as the **Delivery** board, a fixed built-in entry backed by
  `BUDStatus` rather than a row in the new tables.
- It's the only handover target.

**Handover is link-plus-create, not a move.**
- The card stays on its board and lands in a "handed over" stage of category `done`.
- A new BUD is created through the same code path as `POST /buds`. It starts at `bud`,
  `design` or `tech_arch`.
- One card can hand over to, or link, several BUDs. The card shows each BUD's live status and
  a roll-up ("2 of 3 in prod").
- The user can link an existing BUD instead of creating one.

**AI per stage.**
- Each board stage can run a skill when a card enters it, or on demand. The skill comes from
  the same skill library the BUD agents use, through the same agent executor and `ai_runner`.
- The output always waits as a draft for a person to accept, edit or reject. The AI never
  moves a card or hands over.
- The first skills write a PRD and help with initial design. The delivery board keeps its own
  per-stage agent config (`agent_skill_bud_stages`) unchanged.

**Why this shape:**
- **Zero BUD-lifecycle risk.** Nothing that reads `BUDStatus` changes. Release detection,
  XP/SP, learning metrics, estimation and agents keep working on BUDs alone.
- **Skipping ahead keeps the lifecycle honest.** When a handover lands past `bud`, we write the
  skipped moves as ordinary `status_change` timeline events, credited to the person who handed
  over. `sp_pm` and `sp_tech_arch` read exactly those events (`first_status_change_to`), so PM
  and tech-arch SP still work. Phase metrics see the skipped stages as zero-length, and the
  events are tagged `via: handover` so metrics can tell them apart.
- **The card stays the record of the board's own work.** Its history and comments never get
  lost in a move, and the board's throughput counts the handover as done.
- **It avoids the two pitfalls the research keeps finding.** Category-based reporting prevents
  status sprawl. Duplicates are blocked three ways: a BUD has at most one origin card, the
  create call takes an idempotency key, and the dialog suggests similar BUDs to link instead.

## Data model

Everything is org-scoped through `org_id`, using the composite-FK style from `models/team.py`
where it fits. Every status, state or category column is a Postgres enum
(`sa.Enum(PyStrEnum, name=..., values_callable=...)`). User-named stages are rows. All migrations
are autogenerated.

### New enums

| Python enum | PG type | Values |
|---|---|---|
| `BoardStatus` | `board_status` | `active`, `archived` |
| `BoardVisibility` | `board_visibility` | `org`, `members` |
| `BoardMemberRole` | `board_member_role` | `viewer`, `editor`, `admin` |
| `BoardStageCategory` | `board_stage_category` | `todo`, `in_progress`, `done`, `canceled` |
| `BoardCardEventType` | `board_card_event_type` | `created`, `moved`, `moved_board`, `edited`, `assigned`, `unassigned`, `commented`, `archived`, `restored`, `handed_over`, `returned`, `delivered`, `imported`, `doc_updated`, `ai_run` |
| `BoardAttachmentKind` | `board_attachment_kind` | `file`, `link` |
| `BoardHandoverStatus` | `board_handover_status` | `active`, `returned` |
| `BoardCardDocKind` | `board_card_doc_kind` | `prd`, `design_brief`, `notes` |
| `BoardCardDocState` | `board_card_doc_state` | `current`, `pending_review`, `rejected`, `superseded` |
| `BoardAgentTrigger` | `board_agent_trigger` | `on_enter`, `manual` |
| `BoardAgentRunStatus` | `board_agent_run_status` | `pending`, `running`, `completed`, `failed`, `canceled` |
| `TrelloImportStatus` | `trello_import_status` | `pending`, `parsing`, `ready`, `running`, `completed`, `failed` |
| `TrelloCardMapStatus` | `trello_card_map_status` | `imported`, `skipped`, `failed` |

On the categories:
- Four is deliberate, which is fewer than Linear's six. Backlog versus todo is a naming choice
  a board can make with two `todo` stages.
- Triage isn't needed, because the dev side's intake is the `bud` stage.

### Tables

**`boards`**
- `id`, `org_id`
- `name` (150)
- `key` (2–10 uppercase letters, unique per org; `BUD` and `BUG` are reserved)
- `description`, `status`, `visibility`
- `handover_enabled` (bool, default false)
- `handover_stage_id` (FK `board_stages`, must be `done`)
- `return_stage_id` (FK `board_stages`, must be `todo`)
- `handover_target_status` (the existing `bud_status` PG type with `create_type=False`, limited
  in the service to `bud`, `design` or `tech_arch`; default `bud`)
- `ai_enabled` (bool, default false): a board-wide kill switch for every stage agent
- `created_by`, timestamps
- Unique `(org_id, key)` and `(org_id, name)`.

**`board_stages`**
- `id`, `org_id`, `board_id`
- `name` (60), `category`
- `position` (int)
- `wip_limit` (nullable int, soft)
- `is_default` (where new cards land)
- Unique `(board_id, name)`.
- Service rules: at least one `todo` and one `done` stage, exactly one default, and a soft cap
  of `BoardsConfig.max_stages_per_board` (default 8).

**`board_members`**
- `board_id`, `user_id`, `org_id`, `role`
- Composite FK `(user_id, org_id)` to `org_to_user`, so offboarding cascades the same way
  `team_members` does.

**`board_teams`**
- `board_id`, `team_id`, `org_id`, `role`
- Composite FK `(team_id, org_id)` to `teams`.
- Everyone in the team gets that role on the board. If someone has both an individual row and
  one or more team rows, the highest role wins.
- Teams are generic (`TeamRepo` is optional), so an SEO team with no repos works fine.

**`board_user_prefs`**
- `board_id`, `user_id`, `org_id`
- `starred` (bool), `last_opened_at`, `filters` (JSONB)
- Unique `(board_id, user_id)`.
- One row holds three per-person things: whether they starred the board, when they last opened
  it, and the filters to restore when they switch back. Together these drive the switcher and
  the sidebar.

**`board_labels`**
- `id`, `org_id`, `board_id`, `name`, `color`.
- `color` is a `BoardLabelColor` Postgres enum, rendered through `label-*` theme colours defined for light and dark in `plugins/vuetify-theme.ts`. No hex values in data.

**`board_cards`**
- `id`, `org_id`, `board_id`, `number`, `stage_id`
- `position` (float8, gap-based, rebalanced per stage when the gap gets too small)
- `title` (500), `description_md`
- `priority` (the existing `bud_priority` PG type, nullable, meaning no priority). A handover
  carries it straight onto the BUD, falling back to P2.
- `start_at`, `due_at`, `due_done`
- `started_at` (first entry into an `in_progress` stage)
- `completed_at` (entry into `done` or `canceled`; cleared on reopen)
- `archived_at`, `created_by`, timestamps
- Unique `(board_id, number)`.
- Indexes:
  - `(board_id, stage_id, position) WHERE archived_at IS NULL`
  - `(org_id, due_at) WHERE completed_at IS NULL AND archived_at IS NULL`, for reminders
  - a `pg_trgm` index on `title`, for search
- The join tables get `board_card_assignees(user_id, card_id)` and
  `board_card_labels(label_id)`.
- The display key is `f"{board.key}-{number}"`.
- **Numbering never reuses a number.** `boards.next_card_number` is a counter that only goes up.
  `BoardCardRepository.allocate_card_numbers(board_id, n) -> range` claims numbers with one
  `UPDATE … RETURNING`.
  - `max + 1` would hand out `SEO-14` again after the original `SEO-14` moved to another board
    and became an alias.
  - It also lets a Trello import reserve thousands of numbers in one statement.

**`board_card_assignees`** and **`board_card_labels`**
- Join tables. Cards can have several assignees, since imported cards often do. BUDs keep their single assignee.

**`board_card_checklist_items`**
- `id`, `org_id`, `card_id`
- `group_name` (Trello checklists have names), `text`, `done`, `position`.

**`board_card_comments`**
- `id`, `org_id`, `card_id`
- The columns come from a shared `CommentColumns` mixin, the same one bug comments move onto:
  - `author_id` (nullable for imported comments)
  - `author_label` (e.g. "Priya (Trello)")
  - `body`, `created_at`, `edited_at`
  - `deleted_at`, for tombstone deletes

**`board_card_attachments`**
- `id`, `org_id`, `card_id`, `kind`
- `url` for links. For files, a shared `AttachmentColumns` mixin that bug attachments move
  onto: `storage_path`, `filename`, `mime_type`, `size_bytes`, `uploaded_by`.
- Files go through `services/file_storage.FileStorage`, exactly as `bug_attachments` do.

**`board_card_events`**
- `id`, `org_id`, `card_id`, **`board_id`** (frozen at write time), `type`, `actor_id`
- `actor_label`, for imported actions
- **`from_category`**, frozen alongside `to_category`, so per-board metrics stay correct after a
  card moves between boards
- Indexes: `(org_id, board_id, to_category, created_at)` and `(card_id, created_at)`.
- `edited` events from the same person within `BoardsConfig.edit_coalesce_seconds` merge into
  one.
- `from_stage_id`, `to_stage_id`
- **`to_category`**, frozen at write time
- `detail` (JSONB), `created_at`
- Freezing the category makes cycle-time and throughput reports immune to someone
  re-categorising a stage later. That's the category-drift pitfall.

**`board_card_handovers`**
- `id`, `org_id`, `card_id`, `bud_id` (FK `bud_documents`, `SET NULL`)
- `status`, `linked_existing` (bool)
- `handed_over_by`, `handed_over_at`
- `returned_by`, `returned_at`, `return_reason`
- `idempotency_key` (UUID from the client, unique per org), so a double click or retry never
  creates a second BUD
- Unique `(card_id, bud_id)`. A card can hold many handovers.
- A partial unique index on `bud_id WHERE status = 'active'` means a BUD has one origin card.

**`board_card_key_aliases`**
- `org_id`, `key` (e.g. `SEO-14`), `card_id`
- Unique `(org_id, key)`.
- When a card moves to another board it gets a new key. The old key stays here, so links,
  Slack messages and MCP calls that use it still resolve.

**`board_card_docs`**
- `id`, `org_id`, `card_id`, `kind`, `state`, `version`
- `body_md`
- `source` (the existing `bud_edit_source` type: `ui`, `mcp`, `agent`, and so on)
- `agent_run_id` (nullable), `created_by`, `reviewed_by`, `reviewed_at`
- A partial unique index on `(card_id, kind) WHERE state = 'current'`.
- This is where the AI's PRD and design brief live, so agent output never overwrites the
  card's description. At handover, the current PRD becomes the BUD's `requirements_md`, and the
  design brief goes into the BUD's design context.

**`board_stage_agents`**
- `id`, `org_id`, `stage_id`, `skill_id`
- `execution_order`, `trigger`
- A stage has at most one `on_enter` agent, enforced by a partial unique index on
  `(stage_id) WHERE trigger = 'on_enter'`. It can have any number of `manual` agents.
- The rule exists because one active run per card means a second `on_enter` agent could never
  be queued.
- `enabled`, `created_by`
- Unique `(stage_id, execution_order)`.
- This is the board counterpart of `agent_skill_bud_stages`.

**`board_card_agent_runs`**
- `id`, `org_id`, `card_id`, `stage_id`, `stage_agent_id`, `skill_id`
- `status`, `job_id`, `attempt`
- `result_summary`, `error_message`, `triggered_by` (null for `on_enter` runs),
  `started_at`, `finished_at`
- A partial unique index on `card_id WHERE status IN ('pending', 'running')` means one active
  run per card. It mirrors `uq_bud_agent_tasks_one_active`, but with an enum status.

**`external_import_sessions`** (generic: Trello is the first source; Jira can move over later)
- `id`, `org_id`, `board_id` (target, nullable until created), `status` (PG enum)
- `source_kind` (PG enum `import_source_kind`: `trello`; values added per source later)
- `mode` (PG enum: `upload`, `api`)
- `storage_path` (the uploaded file)
- `config` (JSONB list→stage and member→user mappings, archived-card choice)
- `discovery` (JSONB summary)
- `total_cards`, `processed_count`, `last_processed_index`
- `job_id`, `error`, `created_by`
- Mirrors `jira_import_sessions`, but with enum status and source.

**`external_item_maps`**
- `org_id`, `session_id`, `source_kind`, `external_id`, `target_board_id`, `card_id` (SET NULL),
  `status` (PG enum), `error`
- Unique `(org_id, source_kind, external_id, target_board_id)`. Re-imports are idempotent, and
  the same Trello board can still be imported into a second board.

**`digest_claims`** (generic: due reminders first; the leave digest can move over later)
- `kind` (PG enum `digest_kind`: `board_due`), `org_id`, `user_id`, `day`, `status`, `error`
- Unique `(kind, org_id, user_id, day)`. Claiming before sending makes reminders idempotent per
  person per day, even for cards with several assignees.

is the only source of truth for where a BUD came from.

can't be deleted while they're set.

`returned_to_board`. They need no migration because `bud_timeline_events.event_type` is
`String(30)`.

## Permissions and visibility

Today every check is an org-wide role permission (`core/permission_deps.require_permissions`).
Every engineering router sits behind `workspace:engineering` (`api/router.py:182`), which the
`sales` and `hr` roles don't have. Boards bring in **the first per-object access rule** in the
codebase, so it has to live in one place.

### A new permission category, `BOARDS`

Defined in `core/permissions.py`:

| Permission | Purpose | Notes |
|---|---|---|
| `boards:view` | Open the boards area and see org-visible boards | `backfill_custom_roles=True`, granted to every default role, including sales and HR |
| `boards:create` | Create a board (the creator becomes its admin) | org_owner, admin, pm, manager, tech_lead, designer |
| `boards:manage` | Admin on every board, including members-only ones | org_owner, admin |

### Per-board role

One rule, written once as SQL in `BoardAccessRepository.role_subquery` (see Architecture rules). `resolve_board_role` is a thin wrapper over `role_for`:

1. `boards:manage` → `admin`.
2. The highest role from the user's `board_members` row and from every `board_teams` row for a
   team they belong to.
3. `visibility = org` and `boards:view` → `viewer`.
4. Otherwise `None`. The API returns **404, not 403**, so members-only boards don't leak their
   existence. Someone who can see the board but whose role is too low for the action gets
   **403**, since they already know it exists. A write to an archived board gets **409**.

What each role can do:

| Role | Can |
|---|---|
| viewer | View and comment, but not edit |
| editor | Create, edit, move and archive cards; accept or reject AI drafts; run a stage's AI by hand |
| admin | Edit settings, stages, members, teams and labels; configure AI per stage; import; archive the board |

List endpoints use a repository method that filters to boards the user can see in SQL, so a
board never gets fetched first and filtered afterwards.

Teams stay managed where they are today (`api/v1/teams.py`, `team:manage`). A board admin
picks from existing teams; they don't create them.

### Routing and landing

- The boards router mounts **outside** `engineering_router`, under `/api/v1/boards`, gated by
  `boards:view`.
- The handover endpoint additionally requires `workspace:engineering` and `buds:create`, checked
  explicitly. A non-code person can run a board without being able to create BUDs.
- On the frontend, the new routes live in `router/routes/boards.ts` with
  `meta.permission = 'boards:view'` and no `meta.workspace`.
- A "Boards" link goes into both the engineering nav and the people nav.
- `/me` gains a `has_boards` flag. `homeRouteFor` in `utils/workspace.ts` sends engineering users
  to the dashboard as now, others with `has_boards` to `/boards`, and everyone else to leave.

## Architecture rules

These came out of a senior architecture review that checked the plan against the code. They
override anything looser elsewhere in this document.

### Board access: one rule, in SQL, enforced by types

- **The rule is written once, as SQL**, in `repositories/board_access.py`:
  - `BoardAccessRepository.role_subquery(user_id, perms) -> Subquery` returns
    `(board_id, role)`. It takes `max(role)` across the individual and team rows (Postgres
    orders enum values as declared), adds `viewer` for org-visible boards, and `admin` for
    `boards:manage`.
  - `role_for(board_id, user_id, perms)` and `users_with_access(board_id, user_ids)` build on
    it.
  - The board list, the switcher, by-key lookup and MCP `list_boards` all use the same
    subquery.
  - Nothing re-implements the rule in Python.
- **Handlers get access through a dependency.** `core/board_deps.require_board(min_role)` is a
  FastAPI dependency that returns a frozen `BoardAccess(board, role, user_id, org_id)`.
  - Every board service function takes a `BoardAccess` argument, so mypy refuses any call path
    that skipped the check.
  - MCP handlers build the same `BoardAccess` through one helper.
- **Actions map to roles in one table.** `BOARD_ACTION_MIN_ROLE: Mapping[BoardAction,
  BoardMemberRole]` in `services/boards/constants.py`.
  - The board API returns `capabilities: list[BoardAction]`.
  - The frontend shows or hides controls from that list and never copies the role matrix.
- **WebSockets.**
  - `api/v1/ws.py`'s `_owns_topic_bud` becomes a registry, `SCOPE_CHECKS: dict[Scope,
    Callable[[str, Subscriber], Awaitable[bool]]]`. The `board` scope calls `role_for`.
  - `Subscriber` gains `permissions: frozenset[str]`.
  - Removing a member, or a team losing access, drops that user's `board:<id>` subscriptions on
    the server.
- **Notification recipients.** Every list is intersected with `users_with_access` before
  `list_slack_recipients`, so people removed from a board stop getting its DMs and reminders.
  Org-wide topics carry no content from members-only boards (see the Garden section).

### Shared building blocks, built now because boards are the second user

- **Comments and attachments.**
  - SQLAlchemy mixins, `CommentColumns` and `AttachmentColumns`.
  - A generic `ThreadRepository(BaseRepository[C])`, built as
    `ThreadRepository(model, parent_col, db, *, org_id)`.
  - A small route factory for list, create, edit and delete.
  - Bugs move onto all three. Cards are the second user. BUDs can follow later.
  - On the frontend: `createCommentThread(baseUrl, error, onCountChange)` and
    `useAttachmentStrip({ baseUrl, staged, setStaged })`. `limits.maxFilesPerBug` becomes
    `maxFiles`.
  - Separate tables keep foreign-key cascades and composite org keys. That's why this isn't
    one polymorphic table.
- **The agent executor.** `services/agents/executor.execute_agent_run(job_id, run, subject:
  AgentSubject)`, with `AgentSubject` a Protocol of `build_prompt`, `handle_output` and
  `mcp_grant`. BUD and card agents both run on it.
- **External imports.** `services/imports/` has an `ImportSource` Protocol (`discover`,
  `iter_items`, `write_item(item, ctx)`), one session table and one map table, both keyed by a
  source enum. Trello is the first source.
  - `ImportContext(silent=True)` turns off notifications, assignment DMs, `on_enter` agents and
    socket chatter for every write during an import.
  - A cap of `BoardsConfig.import_max_attachment_bytes` per import, with attachments streamed
    to `FileStorage`.
- **Scheduling.** `services/scheduling/tick_loop.run_tick_loop(...)` and
  `DigestClaimRepository.claim(kind, user_id, day) / finish(...)`.
- **Notices.** A generic `services/notifications/notice.py`:
  - `Notice(org_id, user_ids, category, slack_text, events).send()` after commit.
  - `stage_notice(db, *, org_id, user_ids, type, title, deep_link, category)`.
  - Leave builds its leave-only fields on top. `leave/notify.py` is already 202 lines.
- **Frontend.**
  - `useTopicChannel<E>(topic, handlers, onResync)` for socket channels. There are nine
    `use*Socket` composables today; the board doesn't add a tenth.
  - `common/ActivityTimeline.vue` with a `renderers` map. `BUDTimeline` registers its rows,
    which shrinks it from 553 lines.
  - `common/DiffView` and `common/VersionRail`, extracted from `BUDSectionDiffDrawer`
    (581 lines).
  - `ImportWizardShell` for steps, progress and review. Trello uses it now; Jira's 588-line
    wizard can move later.
  - The boards list is a TypeScript union, `BoardListItem = CustomBoard | DeliveryBoard`, not a
    special-cased stub.

Not abstracted yet: card events keep their own table, and card docs stay specific to cards.
A `DraftReviewService` gets extracted only when BUD sections adopt drafts.

### No hardcoded values

- **`BoardsConfig(BaseSettings)`** in `config.py`, with env prefix `BOARDS_`:
  - board shape: `max_stages_per_board`, `stage_page_size`;
  - positions: `position_gap`, `position_epsilon`;
  - events: `edit_coalesce_seconds`;
  - metrics: `aging_days`, `metrics_window_days`;
  - switcher: `switcher_other_limit`, `prefs_touch_interval_seconds`;
  - imports: `import_max_upload_bytes`, `import_max_attachment_bytes`,
    `trello_requests_per_10s`;
  - reminders: `due_reminder_default_time`.
- **`services/boards/constants.py`:**
  - `RESERVED_BOARD_KEYS` and `BOARD_KEY_PATTERN`.
  - `HANDOVER_LANDING_STATUSES`, derived from the `BUDStatus` order. Send back uses the same
    constant.
  - `BOARD_ACTION_MIN_ROLE`.
  - `BOARD_AGENT_TYPES`.
  - Trello list-name hints go in `services/imports/trello/constants.py`.
- **Data, not code.**
  - Board templates are YAML files.
  - The `boards:create` default roles go in the role seeder's grant map.
- **Theme tokens.**
  - Label colours: `label-*`.
  - Stage categories: `category-todo`, `category-in-progress`, `category-done` and
    `category-canceled`. The existing `stage-*` colours stay for BUDs only.
- **Frontend constants** in `constants/boards.ts`: sidebar starred limit (7), recent limit (5),
  the switcher key (`B`).
- **Socket event names** are a `BoardSocketEvent` StrEnum, mirrored as a TypeScript union.
- **Similarity thresholds** are imported from `jira_dedup` and `bug_linker`, never redefined.

### Scale

- **Board load.** One `list_summaries` query per stage page. Each stage is keyset-paged on
  `(position, id)`. Columns have a fixed height and scroll on their own, loading the next page
  as you reach the bottom. There's no DOM windowing, because windowing conflicts with SortableJS
  drag and drop. Paging keeps a 4,000-card backlog light.
- **Positions.** float8 with midpoint inserts.
  - When a gap falls below `position_epsilon`, the stage is rebalanced with
    `row_number() * position_gap`, under `SELECT … FOR UPDATE` on the stage row.
  - A rebalance sends `stage_reordered`, so clients resync.
  - LexoRank isn't needed at 5,000 cards per stage.
- **Switcher.** "Other boards" is capped at `switcher_other_limit`; searching beyond that hits
  the server. `last_opened_at` is written at most once per `prefs_touch_interval_seconds`.
  `board_user_prefs.filters` is validated by a Pydantic `BoardFilters`, with a size cap.
- **Handover side effects run after commit.** That covers assignment, the stage-agent job and
  DMs, all through the `Notice`. An in-memory job never reads a row before it exists.
- **Jobs.**
  - The in-memory queue holds 50 jobs. A burst of cards entering an `on_enter` stage can hit
    `QueueFull`. When it does, the run stays `pending` and a sweeper retries it.
  - At startup, one generic `recover_stuck_runs(model)` marks interrupted runs failed, so they
    can be retried.
  - The event bus, socket fan-out and job queue all assume a single backend process. Running
    more than one needs Redis pub/sub and a durable queue. That's out of scope here, and
    written down so nobody assumes otherwise.

### Layering and file size

- **The API is a package, `api/v1/boards/`**, with one module per area:
  - boards, stages, members, labels;
  - cards, card sub-resources, docs;
  - agents, handover, imports, prefs.
  - Schemas use the same package layout.
- **Send back** goes in a new `BUDSendBackAction.vue`. `BUDWorkflowActions.vue` is already 446
  lines, so it doesn't grow.
- **BUD API extractions.** The create, discard and stage-jobs services move out of
  `api/v1/bud.py` (2,331 lines). The new board code doesn't copy its shape.
- **The board store** is modelled on a small store, not on `stores/bud.ts` (752 lines).
- **Garden route access** uses the existing `RouteMeta.permission` array, which already means
  "any of": `permission: ['workspace:engineering', 'boards:view']`. There's no change to
  `workspace`.

## Reuse map

A lot of what boards need already exists. The rule:

- Reuse a component as-is when it's already generic.
- Generalise it in place when it's BUD- or bug-typed but its shape fits. Generalising means

## Moving cards: validation and quick edits

These were decided on 2026-10-31 after a first hands-on test.

- **Checklist before Done.** A card can't enter a stage of category `done` while its checklist
  has open items, unless the person confirms. The server refuses the move with 409
  `CHECKLIST_OPEN` and the open count. The client asks "N checklist items are still open. Move
  to <stage> anyway?" and resends with `confirm_open_checklist: true`.
- **Required fields per stage.** Each stage can list fields a card must have before it enters:
  `board_stages.required_fields`, an array of the PG enum `stage_required_field` (`assignee`,
  `due_date`, `priority`, `label`, `description`, `prd`).
  - **Where it's checked.** Moves and creates into that stage. The server refuses with 422
    `STAGE_REQUIREMENTS_MISSING` and the missing list.
  - **On the board.** `CardSummary` carries `has_description` and `has_prd`, so the board can
    check before a drop. A refused drop animates back, and a message names what's missing, with
    "Open card".
  - **Exceptions.** Moving cards out of a deleted stage (`move_to`) and imports
    (`ImportContext`) don't check requirements. Admins set requirements in Stages settings.
- **Due date from the board.** The card's date chip, or a calendar "+" when the card has no due
  date, opens a date picker for anyone who can edit. It can set, change or clear the due date and
  saves through the card PATCH, optimistically with rollback.
- **Delivery is a board type.** The BUD board is listed under Boards as the "Delivery" board
  (type Delivery, key BUD), first in the sidebar's Boards section for engineering users and no
  longer in Work. It uses the same board chrome as custom boards: breadcrumb, title switcher, key
  chip and meta line. `/boards/BUD` redirects to `/buds`. Data and the BUD lifecycle are
  unchanged, and BUDs don't gain a board id.
- **Assign from the board.** A card's avatars, or a "+" when no one is assigned, open a people
  picker for anyone who can edit. It lists people with access to the board and saves through
  the card PATCH, optimistically with rollback.

## Moving cards between boards

A card can move between two custom boards, for example SEO to DevOps. It's the same row moving,
so its comments, checklist, attachments, docs, events and handovers all stay. The rules:

- **Who.** An editor on both boards.
- **Stage.** A stage with the same name on the target, else the first stage of the same
  category, else the target's default stage.
- **Key.** The card gets the target board's next number. The old key goes into
  `board_card_key_aliases`, so `SEO-14` still resolves after the card becomes `OPS-3`.
- **Labels.** Matched by name on the target. Unmatched labels are dropped and listed in the
  `moved_board` event.
- **Assignees.** Anyone who can't edit the target board is removed, and listed in the event.
- **AI.** An active agent run is canceled first. The target stage's `on_enter` agents then run
  as usual.
- **Events.** A `moved_board` card event, and `card_left_board` and `card_created` on the two
  board topics.

Moving a card to the Delivery board isn't a move. It's a handover.

## Handover flow

### Handing over

1. On a board with `handover_enabled`, an editor who also holds `workspace:engineering` and
   `buds:create` clicks **Hand over to dev** (or **Hand over another**).
2. **Preview.**
   - The BUD title is the card title.
   - `requirements_md` is the card's current PRD doc, or its description when there's no PRD.
     After it comes a "From the board" section: the checklist as a markdown list, attachments
     as links, the design brief if there is one, and a link back to `SEO-14`.
   - The first link attachment on a Figma URL becomes `figma_url`.
   - We embed the draft and run the existing pgvector similarity search against open BUDs,
     importing the existing thresholds (`jira_dedup.THRESHOLD_REVIEW`, `bug_linker.AUTO_LINK_THRESHOLD`) rather than redefining 0.40. It uses the new top-K `BUDRepository.find_nearest_active(vec, limit)`. The preview's embedding is passed on to `create_bud_from_input`, so the text isn't embedded twice.
   - When the target is `tech_arch`, the preview requires a non-empty PRD or description. The
     tech planner has nothing to work from otherwise.
3. **Confirm.** One transaction does the following:
   - **Create mode.**
     - Call a new shared `services/bud_create.create_bud(...)`. It's extracted from today's
       `POST /buds` path, so numbering, embedding, timeline `created` and any create-time
       behaviour run exactly as they do now.
     - The BUD is created at `bud`. Its initial `bud_versions` row has
       `edited_by = handing-over user`, which keeps BUD authorship attribution right.
     - We add a `handed_over_from_board` timeline event.
   - **Landing past `bud`** (`services/boards/handover_landing.py`). For each skipped stage in
     order (`bud → design`, then `design → tech_arch`), we write an ordinary `status_change`
     timeline event with `actor_id` set to the handing-over user and `detail.via = "handover"`,
     then set the status.
     - Then we run assignment and the agent trigger for the **target stage only**. That's
       `auto_assign_for_phase` and the shared stage-jobs function, extracted from
       `_trigger_status_jobs` in `api/v1/bud.py`.
     - Agents for the skipped stages don't run. The board already did that work.
     - `sp_pm` and `sp_tech_arch` find their "first move to design" and "first move to
       development" events in the timeline as usual (`first_status_change_to`). So PM credit
       for the requirements goes to the person who handed over.
   - **Link mode.** Leave the BUD untouched apart from a timeline event. It's refused if that
     BUD already has a different live origin card.
   - Insert the `board_card_handovers` row. Its `idempotency_key` makes a retry or double click
     return the first result instead of creating a second BUD.
   - On the card's first handover, move it to `handover_stage_id`, which is category `done`. In
     every case, write a `handed_over` card event.
4. **After commit.**
   - Slack-DM the BUD's assigned owner ("SEO-14 was handed over as BUD-123").
   - Publish `board:<id>` and the usual BUD events.

### What carries over and what doesn't

| Item | What happens |
|---|---|
| Title, PRD or description, checklist, attachments, design brief | Copied once into the BUD. The card keeps its originals. |
| Priority | The card's priority becomes the BUD's priority, falling back to P2. |
| Comments and history | Stay on the card. The BUD's Origin panel shows them read-only. Nothing is duplicated, so nothing drifts. |
| Assignees | Not copied. The BUD's existing auto-assignment picks the owner for the target stage. Card assignees get notified about each BUD's progress. |
| Labels, start and due dates | Not copied. BUDs have no labels, and their dates come from estimation. |

After handover, the card's description and docs can still be edited, but those edits don't
reach the BUDs. The BUD is the source of truth for delivery.

### Bouncing back

Return works one BUD at a time. It's only allowed while that BUD is in `bud`, `design` or
`tech_arch`, which means before development starts. That follows the "only send back for
structural problems" rule from the research.

1. Someone with `buds:edit` clicks **Send back** and gives a reason.
2. The BUD is discarded through a shared `services/bud_discard.discard_bud(...)`, extracted from
   today's DELETE handler, so `transition_feature_for_bud(..., DISCARDED)` and the other side
   effects run as they do now. We add a `returned_to_board` timeline event.
3. The handover row becomes `returned`, with the reason. A `returned` card event and a comment
   carry the reason, and card assignees get notified.
4. If no other active handover remains on the card, it moves to `return_stage_id` (category
   `todo`). Otherwise it stays where it is.
5. **Handing over again** reuses that BUD if it's still discarded. It restores the BUD through
   `services/bud_restore.py`, writes a new version with the refreshed requirements, and sets the
   handover back to `active`. The BUD number is reused, so no duplicate is created.

Once development has started, work never moves back to the board. Problems are handled inside
the BUD (bugs, comments, the existing bounce from testing to development).

If the dev side discards a BUD for its own reasons, the handover row stays `active`. The card's
chip shows "BUD-123 discarded", and the existing BUD restore brings it back.

### Delivered

`on_bud_closed` is already the single entry point for both prod and close, from both the manual
PATCH and the auto-close. It gains one call, `services/boards/notify.notify_origin_card(bud)`,
wrapped in the same swallow-and-log pattern as its other steps. It does three things:

- writes a `delivered` event on the card for that BUD (idempotent, by checking for the event);
- notifies the card's assignees;
- when every active handover on the card has reached prod, marks the roll-up as fully delivered.

No XP and no SP are involved.

## AI on board stages

### What it does

Each stage of a board can have one or more agents, stored in `board_stage_agents` and set up in
the board's AI settings tab. An agent has:

- **A skill.** Skills are `agent_skills` rows keyed by the `agent_type` Postgres enum and seeded
  from `AGENT_SKILL_MAP`. There are two new values, `AgentType.BOARD_PRD` and `BOARD_DESIGN`
  (`ALTER TYPE agent_type`), backed by two new `.md` files. The stage picker offers skills whose
  type is in `BOARD_AGENT_TYPES`.
- **A trigger.**
  - `on_enter`: runs when a card enters the stage, whether by drag, by "Move to…" or by a move
    between boards.
  - `manual`: runs from the card's "Run AI" button.

The output always lands as a `pending_review` doc. A person accepts, edits or rejects it, and
nothing changes on the card until then. The AI never moves a card and never hands over.

### How a run works

1. `services/boards/agents/trigger.py` checks two things. The board's `ai_enabled` switch must
   be on. The card must have no active run, which the partial unique index enforces. If both
   pass, it inserts a `board_card_agent_runs` row and enqueues `JOB_BOARD_AGENT_RUN`, using the
   same `register_job_type` pattern as other jobs.
2. The run goes through a shared executor, `services/agents/executor.execute_agent_run(job_id,
   run, subject)`. It's extracted from `bud_agent_handler.py` (616 lines) rather than copied, and
   calls `ai_runner.run_agent_for_org_id`. That way the org's provider, Claude or another, and
   its capability gate apply exactly as they do for BUD agents.
   - The card side implements `AgentSubject`: `build_prompt`, `handle_output` and `mcp_grant`.
   - The BUD handler moves onto the same executor in the same milestone.
3. The skill writes through the MCP `write_card_doc` tool with a token whose grant covers only
   that card and that tool.
   - Some providers have no MCP, and some smaller models never call the tool. In either case
     `handle_output` saves the output as a `pending_review` doc, the same fallback
     `handle_prd_result` uses.
4. `apply.py` records an `ai_run` card event and publishes `doc_updated` and
   `agent_run_updated`. It also publishes on `agent_activity:<org_id>`, which the Garden already
   shows for BUD agents. It notifies the card's assignees that a draft is waiting.

### Guard rails

- A failed run leaves the card where it is, records the error on the run, notifies the card's
  assignees, and offers Retry.
- Every accepted draft is a new doc version, so it can always be reverted from the version
  history. The activity feed shows which run produced what.
- There's no run cap for now. One active run per card, no agents on import, and the board-wide
  `ai_enabled` switch are the controls.
- Only board admins can configure agents. Editors can run manual agents and review drafts.
- Skills declare their tools in frontmatter (`tools:` and `mcp_tools:`). Before adding the
  board skills, check that `claude_guard` doesn't deny anything they declare.
- AI runs earn no XP and no SP.

### First skills

- **`board-prd-writer.md`** reads the card's title, description, comments and attachments, plus
  related features through `get_features`, and writes a `prd` doc. It follows the product
  manager skill's rules: short, testable acceptance criteria, and no invented names.
- **`board-design-helper.md`** reads the card and its PRD, plus the org's design systems through
  `list_design_systems` and `get_design_system`, and writes a `design_brief` doc. The brief
  covers user flows, screens, states and edge cases, as a starting point for a designer. At
  handover it travels into the BUD, so the BUD's design stage starts from it.

### Building WordPress pages for SEO

A skill that drafts and publishes WordPress pages for SEO cards gets its own follow-up plan. The
engine above is built to carry it: per-stage config, run records, doc versions
and run records. The follow-up covers:

- WordPress credentials (application passwords stored with `encrypt_secret`);
- draft versus publish per stage;
- reverting a published page;
- SEO checks before publishing.

## Trello import

We do a one-time import with a cutover. Ongoing sync is out of scope:

- Two-way sync is where duplicates and loops come from.
- Webhooks need a public URL that local-first installs often don't have.
- Running two tools at once is what we're trying to end.

The cutover is simple: import, check, close the Trello board. Running the import again only
picks up cards added in the gap, because `external_item_maps` makes it idempotent.

Both modes are built. They share the parser output shape, the review screen and the import job.
Only the extract step differs.

### Upload mode (JSON)

1. A board admin, or anyone with `boards:create` for a new board, uploads the board's JSON
   export. The size cap is `BoardsConfig.import_max_upload_bytes` (default 50 MB).
2. The parse job (`JOB_IMPORT_DISCOVER`, generic across sources, registered in `services/job_handlers.py`) reads the file
   and fills `discovery`: lists, labels, members, card and comment counts, and a warning flag
   when the action count hits 1,000, since older comments are then missing. The warning
   suggests API mode.
3. **The review screen is where the import gets shaped.**
   - **Lists → stages.** Each open list becomes a new stage with the same name. We pre-fill a
     category with a simple rule:
     - the last list, or a name matching done/complete/shipped/published → `done`;
     - doing/progress/review/writing → `in_progress`;
     - otherwise → `todo`.
     The user confirms or changes each one, or maps several lists into one stage. Archived lists
     are skipped by default.
   - **Members → users.** We suggest a match by full name against org users, since Trello
     exports don't include emails. Unmatched members become unassigned, and their comments keep
     an `author_label`.
   - **Archived cards.** Skip them, or import them as archived.
   - **Target.** A new board, or an existing board the user is admin on.
4. The import job (`JOB_IMPORT_RUN`, generic, under `ImportContext(silent=True)`) writes cards in batches and records
   `last_processed_index`, so a restart can resume. That matters because the job queue is in
   memory, the same as the Jira import.
5. Imported cards don't trigger `on_enter` agents. An import shouldn't start hundreds of AI runs.

### API mode

This mode closes the gaps in the JSON export: full comment history and real file attachments.

- **Credentials.** An org admin with `integrations:configure` pastes a Trello API key and a
  read-scoped token. They're stored encrypted with `encrypt_secret` under
  `org.config["trello"]`, the same shape as `config["jira"]`, so the existing secret rotation
  re-encrypts them with no extra wiring.
- **Picking a board.** The user picks from their Trello boards (`/1/members/me/boards`).
- **Fetching.** The board comes from the nested `GET /1/boards/{id}`. Comments are paged from
  `/actions?filter=commentCard` with `before` and de-duplicated by id. Files are downloaded
  with the `Authorization: OAuth` header into `FileStorage`, subject to the existing
  attachment size limits.
- **Throttling.** A client-side limiter keeps requests at `BoardsConfig.trello_requests_per_10s` (default 80), under the
  100-per-token limit, and backs off on 429.

### Field mapping

| Trello | Glideship |
|---|---|
| list | stage |
| card `name`, `desc` | `title`, `description_md` (Trello descriptions are already markdown) |
| `pos` | `position`, in source order |
| `idMembers` | assignees, through the member mapping |
| `labels` | board labels, matched on name, with the colour mapped to the nearest palette entry |
| `start` | `start_at` |
| `due`, `dueComplete` | `due_at`, `due_done` |
| (no Trello field) | `priority` left empty |
| checklists | checklist items, with `group_name` set to the checklist name |
| `commentCard` actions | comments, keeping the original date and the mapped author |
| attachments | links in upload mode; files (uploads) or links (URLs) in API mode |
| `closed` | `archived_at` |
| custom fields, Power-Up data, covers | dropped, and the review screen says so |

Every card gets an `imported` event carrying the Trello `shortLink`.

In upload mode **we never fetch attachment URLs from the uploaded file.** They're stored as links
only. That avoids pulling arbitrary URLs from user-supplied JSON. API mode downloads only from
`api.trello.com` attachment endpoints, using IDs from the API response.

## Notifications

Three new `NotificationCategory` entries go in `services/notifications/categories.py`, following
the three-step recipe in its docstring. All default to on and all require `boards:view`.
Recipients always come from `UserRepository.list_slack_recipients(..., category=...)`, so
opt-outs are respected. DMs go out after commit, following the leave module's `Notice` pattern.

| Category | Sent when |
|---|---|
| `BOARD_CARDS` ("Board cards") | You're assigned to a card; someone comments on a card you're assigned to (not your own comments); an AI draft is waiting for review on your card; an AI run on your card failed |
| `BOARD_HANDOVERS` ("Handovers") | A card is handed over to you as a BUD's owner; a BUD from a card you're on is returned with a reason; a BUD from your card reaches prod |
| `BOARD_DUE_REMINDERS` ("Due dates") | Once each morning: your cards due today and overdue, in one message |

### Due reminders

`services/boards/due_reminders.py` follows the leave digest scheduler
(`services/leave/digest_scheduler.py`):

- It runs on a shared `services/scheduling/tick_loop.run_tick_loop(name, tick_seconds,
  tick_once)`, extracted from the ten `run_forever` loops in `main.py`. `due_local_date` moves
  there too.
- The fire time comes from org config, `boards.due_reminder_time`, falling back to
  `BoardsConfig.due_reminder_default_time`. The timezone comes from the same source as the leave
  digest.
- At fire time it sends one DM per assignee, covering their open cards (not `done` or
  `canceled`) that are due today or overdue.
- It claims `digest_claims(kind=board_due, user_id, day)` before sending, so a restart, a second tick or a card with several assignees never double-sends or skips anyone.
- All the state lives in Postgres, so the scheduler heals itself after a restart.

### In-app notifications

These reuse the `Notification` model, with new `NotificationType` values:
`board_card_assigned`, `board_card_comment`, `board_ai_draft`, `board_ai_failed`,
`board_handover`, `board_handover_returned`, `board_handover_delivered` and `board_due`.

The autogenerated revision gets `ALTER TYPE notification_type ADD VALUE IF NOT EXISTS ...` lines
inside `op.get_context().autocommit_block()`, following `z4_add_code_review_and_commits`.

## XP, SP, metrics and the Garden

**XP.** Card work and AI runs earn no XP. XP is for real dev work. A BUD created by handover
earns XP exactly like any other BUD, through the unchanged `api/v1/bud.py` and `bud_closure.py`
paths.

**SP.** Nothing new is awarded.
- When the handover lands at `bud`, `sp_pm` and `sp_tech_arch` fire as they do today.
- When it lands later, the written `status_change` events give them the same signal, credited to
  the person who handed over.
- The handover PR includes tests for both landing points, for `award_pm_sp_on_close` and
  `award_tech_arch_sp_on_close`.

**Learning metrics and estimation.** These read BUDs only.
- Stages skipped at handover show as zero-length phases.
- `bud_metrics_phases` skips `status_change` events tagged `via: handover` when it computes phase
  drift, so skipped stages don't count as "finished early".
- Estimation, which runs from the current status, needs no change.

**Board metrics** are new, in `services/boards/metrics.py` with SQL in the repository. All of
them use `board_card_events.to_category`, never stage names:
- Throughput: cards entering `done` per week.
- Cycle time: first `in_progress` to `done`, as a median and p85.
- WIP by category.
- Aging: open `in_progress` cards older than N days.
- A cross-board summary on the boards index shows the same numbers per board, which works
  because the categories are shared.
- "Idea to prod" lead time, from card creation to each linked BUD reaching prod.

**Garden.** Board activity shows up in the Garden, as ambience only, with no XP.
- **Access.** The Garden view and `/character-select` carry `meta.workspace: 'engineering'`
  today. They switch to `meta.permission: ['workspace:engineering', 'boards:view']` (the array
  already means any one of them), so board-only users can enter. Clicking a BUD in the world opens its details only for engineering users. The PR
  checks that the Colyseus seat-reservation path accepts these users without widening it
  beyond the user's own org.
- `services/boards/garden.py` publishes `board_activity:<org_id>` events for three things: a card
  reaching `done`, a handover, and a delivered BUD.
  - For members-only boards, these events, and the `agent_activity` events from board runs,
    carry no card titles or keys, only the kind of activity and the actor.
- `colyseus_forwarder` gets a rule to forward that prefix, next to `agent_activity`.
- Board AI runs already reach the Garden through `agent_activity`.
- In the engine:
  - any new zone or position (for example a board noticeboard by the existing BUD area) goes in
    `shared/world/` only;
  - celebrations reuse existing KayKit tracks with exact names (`Cheering` on the assignee's
    character when a card is done);
  - all of it follows `frontend/src/engine/ARCHITECTURE.md`.

## Existing BUDs

**No migration.**
- BUDs stay where they are.
- The BUD board becomes the built-in Delivery entry in the boards list, with no data change.
- `org.config.bud_stages` (the UAT toggle) and the BUD stage agent config keep working.
- The permission seeder adds the `BOARDS` category on startup, and `backfill_custom_roles` gives
  existing custom roles `boards:view`.

## Risks

- **The first per-object access rule.**
  - What can go wrong: one endpoint or MCP tool that forgets the check leaks a members-only
    board. Team-based roles add a second path to get wrong.
  - Mitigation: a single resolver, list queries that filter by viewer in SQL, a test per
    endpoint for the 404 case, and an MCP test for each tool.
- **AI drafts accepted without being read.**
  - What can go wrong: a weak PRD gets one-click accepted and then handed over.
  - Mitigation: the accept view shows a diff, every accepted draft is a revertible version, and
    the BUD's own stages still run with people assigned.
- **AI cost with no cap.**
  - What can go wrong: you chose no run cap for now, so spend is bounded only by how much work
    flows.
  - Mitigation: one active run per card, no agents on import, and the board-wide switch. Every
    run is recorded, so a cap can be added later from real numbers.
- **Landing past `bud`.**
  - What can go wrong: written status events could mislead SP or metrics.
  - Mitigation: they use the same `status_change` shape that `sp_pm` and `sp_tech_arch` already
    read, with the `via: handover` tag so metrics can exclude them. There are tests for SP at
    both landing points.
- **Board keys and names are unique per org, so "taken" hints that a board exists.** Anyone who
  can create or rename a board could learn that a members-only board uses a key or name. The
  error is the same generic message whether or not the user can see that board, and never
  names it. Uniqueness makes the hint itself unavoidable, so it's accepted.
- **Team membership is a board-access grant.** Adding someone to a team that holds a role on
  a board gives them that role. `team:manage` is already an escalation permission, so this is
  accepted. Board activity records team membership changes that affect board roles.
- **The workspace boundary.**
  - What can go wrong: boards sit outside `workspace:engineering`, but the handover and the
    Origin panel touch BUDs.
  - Mitigation: those paths check the engineering permissions explicitly, and the Origin panel
    lives on the engineering-only BUD page.
- **Duplicate BUDs, now that one card can have several.**
  - Mitigation: the idempotency key, one origin card per BUD, a duplicate suggestion with a
    link-instead option, and a re-handover that restores rather than re-creates.
- **Two sources of truth after handover.**
  - Mitigation: a one-way copy at handover, the note on the card, and comments kept in one
    place per side.
- **Status sprawl and category drift.**
  - Mitigation: a cap of eight stages, the four-value category enum, templates, and the
    category frozen on each event.
- **Moving cards between boards breaks references.**
  - Mitigation: key aliases, the dropped-data preview, and the same row (and id) throughout.
- **A new frontend dependency.**
  - What can go wrong: the build chain is fussy (vite 6 cap, several lockfiles).
  - Mitigation: check the library against the vite version, update both lockfiles, and replay
    the Dockerfile build, not just `npm run build`.
- **Position precision.**
  - What can go wrong: float gaps shrink with repeated reorders.
  - Mitigation: rebalance a stage once the gap falls below `BoardsConfig.position_epsilon`, in one statement under a stage-row lock.
- **Large boards.** Trello allows 5,000 open cards. Mitigation: paged done and canceled columns,
  and an index on `(board_id, stage_id, position)`.
- **The Trello JSON's 1,000-action cap.**
  - What can go wrong: older comments are dropped without warning.
  - Mitigation: the review screen warns when the cap is hit and points to API mode.
- **The in-memory job queue.**
  - What can go wrong: a restart kills a running import or agent run.
  - Mitigation: durable session and run rows, `last_processed_index` resume, and runs marked
    failed on startup so they can be retried.
- **Duplicate reminders.** Mitigation: the unique `digest_claims` row per person per day.

## Later: autonomous work

Autonomous AI is out of scope for this plan. These are the decisions already made, recorded so
the later plan starts from them:

- A board stage can run its AI with no human approval, and the card can move on by itself.
- An autonomous chain can hand over by itself, as the card's owner, who needs `buds:create`.
- The BUD it creates is AI-driven: no assignee, each stage's agent runs and advances it, and the
  AI asks the owner a question when it needs input.
- A person can take over at any time and hand it back later.
- No run cap.

Still to decide, when the later plan is written:
- whether to build a development agent, so an AI-driven BUD can run end to end;
- who answers a question when the owner is away, whether after some days or while the owner is
  on leave.

The autonomous SEO work, building WordPress pages, belongs to that later plan too.
